0. ¿Es suficiente para presentar? Mi evaluación honesta

Sí, el sistema es sólido para una exposición universitaria. No es una maqueta: tiene backend real con reglas transaccionales, base de datos con integridad a nivel de motor, 4 roles, OCR + IA reales, contratos de API, pruebas automáticas, integración continua y despliegue con Docker. Lo que más impresiona no es la cantidad de pantallas, sino que las reglas de negocio se cumplen aunque alguien intente saltárselas (por ejemplo, no se puede reservar más stock del que existe, y el Kardex no se puede borrar).

3. La arquitectura (lo más importante de explicar bien)

Respuesta corta a tu pregunta “¿módulos, capas o microservicios?”: las tres cosas, en distinto nivel.

  • Arquitectura en capas a nivel de todo el sistema: presentación (React) → lógica de negocio (Spring Boot) → servicios especializados (Python OCR) → persistencia (PostgreSQL).
  • Monolito modular a nivel del backend: una sola aplicación desplegable, dividida en módulos funcionales (paquetes) con dependencias controladas.
  • Un único microservicio: el OCR/Fuzzy Matching, separado porque usa otro lenguaje (Python), otro ritmo de cambio y es pesado/lento. No es “arquitectura de microservicios” general.

Cómo viaja una petición (ejemplo: registrar una venta)

Usuario hace clic→React valida con Zod→TanStack Query llama a /api/v1/ventas→Nginx reenvía al backend→Spring Security valida el JWT y el rol→Controller → Service (transacción)→Repository/JPA → PostgreSQL
  1. React valida el formulario (campos obligatorios, fecha de entrega, cantidades) y envía POST /api/v1/ventas con la cabecera Authorization: Bearer <JWT> y una Idempotency-Key.
  2. Nginx (contenedor frontend) reenvía todo lo que empieza con /api al contenedor del backend.
  3. Spring Security verifica la firma del JWT, saca el usuario y el rol, y comprueba que el rol tenga permiso para ese endpoint (@PreAuthorize).
  4. El Controller convierte el JSON a un objeto y llama al Service; el controller no tiene reglas de negocio.
  5. El Service abre una transacción, bloquea las filas de inventario que va a tocar (bloqueo pesimista), calcula cuánto se puede reservar, crea la venta, el detalle y las reservas.
  6. Si algo falla (stock negativo, regla violada), se hace rollback de todo. Si va bien, commit y se responde 201 con el JSON.

¿Por qué monolito modular y no microservicios? (pregunta típica)

Porque las operaciones de inventario, reservas y Kardex deben ser atómicas (RNF-08 y RNF-15): o se hace todo o no se hace nada. En un monolito eso es una sola transacción de base de datos. Con microservicios necesitarías transacciones distribuidas o sagas, más complejidad y más puntos de falla, sin beneficio para el tamaño de una ferretería. Los módulos dan el orden y permitirían extraer un servicio en el futuro. Está escrito en el ADR-004 con la tabla de alternativas descartadas.

Módulos y capas dentro del backend

Cada módulo es un paquete Java con la misma estructura de 4 capas:

CapaQué haceQué NO hace
controllerRecibe HTTP, valida entrada, llama al servicio, devuelve DTO/JSON.No contiene reglas de negocio ni accede a repositorios.
serviceReglas de negocio y límites de transacción (@Transactional). Coordina con otros módulos.No conoce HTTP.
repositoryAcceso a datos (Spring Data JPA, consultas JPQL/SQL).Solo lo usa su propio módulo.
modelEntidades JPA del dominio (Venta, Cotizacion, Inventario…).No depende de otras capas.
  • Un módulo accede a los datos de otro solo a través del service del otro, nunca a su repositorio.
  • Solo el módulo inventario modifica existencias, reservas y Kardex; los demás le piden la operación.
  • Un paquete comun aporta lo transversal: errores de negocio, manejo global de errores (formato RFC 7807), paginación, idempotencia y tareas programadas.
  • Estas reglas de dependencia se mantienen por convención arquitectónica y revisión de código en cada pull request.

6. Las decisiones técnicas que debes saber defender

Reserva ≠ salida física (stock físico, reservado, libre)

Al vender, el stock no sale: se reserva. La salida real al Kardex ocurre solo cuando el almacén confirma la salida del despacho. libre = físico − reservado. Esto permite prometer sin vender dos veces lo mismo y mantener un Kardex honesto (solo registra lo que físicamente se movió).

  • Si falta stock, la venta reserva lo que hay y el resto queda pendiente de abastecimiento.
  • Cancelar una venta libera reservas sin crear movimientos “ficticios” de Kardex.

Concurrencia: ¿qué pasa si dos vendedores reservan lo mismo a la vez?

Tres defensas en capas: (1) la operación corre en una transacción; (2) se usa bloqueo pesimista (@Lock(PESSIMISTIC_WRITE) = SELECT … FOR UPDATE) sobre las filas de inventario, así el segundo espera al primero; (3) la base tiene triggers de restricción diferibles que, al confirmar, verifican que la suma de reservas nunca supere el stock físico. Aunque hubiera un bug en Java, la base de datos rechaza el estado inválido.

Kardex inmutable

La tabla movimiento_kardex tiene un trigger que solo permite insertar (no UPDATE, DELETE ni TRUNCATE). Un error se corrige con un movimiento contrario con motivo. Así hay trazabilidad completa: quién, cuándo, por qué y a partir de qué operación (recepción, despacho, ajuste, traslado).

Idempotencia

Las operaciones sensibles aceptan una cabecera Idempotency-Key. Si el cliente reintenta (por red lenta o doble clic) con la misma clave, el backend devuelve la respuesta original sin repetir la operación. Evita ventas o recepciones duplicadas. Se guarda en la tabla idempotencia y se limpia a diario.

Contrato primero (OpenAPI)

Cada módulo tiene su YAML OpenAPI. Las pruebas validan que cada respuesta real cumple el contrato, y el frontend adapta sus tipos a él. Hay incluso una prueba que verifica que los parámetros de las herramientas del agente coinciden con los de las operaciones del contrato.

IA con límites

El modelo nunca toca la base de datos ni modifica nada. El agente solo puede invocar funciones de consulta que el backend define y autoriza según el rol (tool calling). Las preguntas simples (alertas, disponibilidad de un producto) se resuelven por reglas sin llamar a Gemini (más rápido y barato). Hay tres proveedores intercambiables: simulado, Gemini e híbrido.

OCR en dos capas

Capa 1 (IA): Gemini lee la imagen y devuelve texto + cantidad. Capa 2 (determinista): normalización + RapidFuzz asigna el SKU y calcula la confianza. Se separó para que la IA no invente códigos de producto (alucinaciones). Además el resultado siempre lo revisa un humano antes de usarse, y el OCR no genera ventas ni movimientos por sí solo.

Comunicación asíncrona: el backend encola el documento después de confirmar su transacción (AFTER_COMMIT); el servicio responde 202 y, al terminar, llama de vuelta con un JWT de servicio de alcance limitado (ocr:resultados:escribir). Una tarea programada marca como “servicio no disponible” los documentos que no responden a tiempo.

Seguridad

  • Contraseñas guardadas como hash (nunca en claro).
  • JWT firmado (HS256) con secreto en variable de entorno; sin token de refresco (se vuelve a iniciar sesión al expirar).
  • Autorización por endpoint y por método; el usuario responsable sale del token, no del cuerpo de la petición.
  • Las credenciales viven fuera del repositorio (.env, no versionado); los puertos de la base y del backend se publican solo en 127.0.0.1.
  • Rol de demostración (ADR-013): reúne los permisos de los 4 roles; está apagado por defecto y se activa con una variable de entorno.

Base de datos

  • 28 tablas (incluye la de Flyway), claves bigint generadas, nombres de restricciones explícitos (pk_, fk_, uq_, ck_).
  • Sin eliminación en cascada y sin borrar entidades de negocio: se desactivan (estado_activo).
  • Valores derivados (libre, totales, pendientes) no se guardan: se calculan, para no tener datos contradictorios. La excepción justificada es cantidad_fisica.
  • Cantidades numeric(14,3) (admite kg y metros) e importes numeric(14,2); estados como varchar con CHECK.
  • Esquema versionado con Flyway (V1–V21), migraciones inmutables: un cambio se hace con una migración nueva.

8. Reglas de negocio clave (para explicar el “por qué” del flujo)

  • Cotización: emitida → aceptada por el cliente → validada por MIGAL (Administrador) → se convierte en una sola venta. También rechazada, cancelada o vencida. No reserva stock.
  • Venta: reserva lo disponible; lo demás queda pendiente de abastecimiento. La fecha de entrega requerida es obligatoria (sirve para planificar compras).
  • Despacho: único y completo por venta; solo se confirma si todo está reservado; al confirmar la salida se genera el Kardex.
  • Cancelación de venta: posible hasta que el almacén confirme la salida; libera reservas; con motivo obligatorio.
  • Compras y recepción: crear una orden no cambia el stock; solo la recepción confirmada lo aumenta. Hay tope por línea (no se recibe más de lo pendiente).
  • Alertas: reglas deterministas sobre stock libre vs. mínimo (no machine learning).
  • Roles: Administrador, Vendedor, Almacenero, Reponedor; el de Demostración los reúne.
OjoLa documentación (ADR-003, requerimientos) es del diseño inicial y el producto evolucionó (p. ej. cancelar/modificar cotizaciones aceptadas, fecha de entrega en la venta, previsto neto). Si el profesor nota una diferencia, la respuesta es: “la decisión original quedó registrada en el ADR; las mejoras posteriores salieron de pruebas con usuarios y están en los pull requests #133–#136”.

9. Límites del sistema y trabajo futuro (dilo tú antes de que pregunten)

  • No incluye: facturación electrónica SUNAT, contabilidad, WhatsApp Business, gestión de flota/GPS.
  • Sin devoluciones tras la salida confirmada ni notificaciones automáticas al cliente (decisión de alcance).
  • OCR/IA dependen de un servicio externo (Gemini): requieren internet, clave y cuota; por eso existe el modo simulado y la revisión humana.
  • Un solo JWT de acceso sin refresco: la sesión se renueva iniciando sesión de nuevo.
  • Despliegue: pensado para un servidor/PC con Docker; la base alojada podría migrar a un servicio gestionado.
  • Mejoras futuras: devoluciones, reportes y tableros, notificaciones, refresco de token, métricas y trazas (observabilidad), extracción de módulos si la carga lo exigiera.

10. Guion de la demostración (≈ 8–10 min)

Preparación (antes de entrar al aula): contenedores arriba (docker compose --profile completo up -d --wait), sesión iniciada con el usuario Demostración, tema claro, zoom del navegador al 110 %, una pestaña por pantalla, y la guía de uso abierta como respaldo.

Disponibilidad→Cotización (stock para decidir)→Aceptar y validar→Venta con fecha→Despacho y salida→Kardex→Compra y recepción
  1. Disponibilidad y alertas (1 min): muestra existencias por ubicación, físico/reservado/previsto y la pestaña “En alerta”.
  2. Cotización (2 min): abre una cotización y señala Stock para decidir (libre, por recibir, previsto neto, “Falta comprar”). Menciona que no reserva.
  3. Aceptar → Validar → Convertir en venta (2 min): cambia de rol mentalmente (Vendedor/Administrador). En la venta, resalta la fecha de entrega requerida y las cantidades pendientes.
  4. Despacho (2 min): genera la orden, imprímela (hoja A4), Confirmar salida y luego Ver movimientos en el Kardex (solo los de esa operación).
  5. Reposición (2 min): pestaña Faltantes de ventas → nueva orden de compra con fecha estimada → recepción en 3 pasos repartida por ubicación; muestra el stock subiendo.
  6. Remate (1 min): Agente de IA con “Productos en stock crítico” y OCR (si hay internet), recalcando que el modelo no toca la base.
ConsejoSi algo falla en vivo, no te disculpes: di “esto es justo la regla de negocio funcionando” si es una validación, o pasa a la guía de uso con capturas. Un fallo manejado con calma impresiona más que una demo perfecta.

11. Preguntas probables del profesor (de básicas a avanzadas)

Básicas

¿Qué problema resuelve?

Centraliza inventario, ventas y compras de una ferretería con 3 ubicaciones, evita vender stock inexistente y deja trazabilidad de cada movimiento.

¿Qué lenguajes usaste?

Java 21 (backend), TypeScript/JavaScript (frontend con React), Python 3.12 (servicio OCR) y SQL (PostgreSQL/Flyway).

¿Qué es una API REST?

Una interfaz HTTP donde cada recurso (ventas, productos) tiene una URL y se opera con verbos (GET consulta, POST crea, PUT modifica). Aquí intercambia JSON bajo /api/v1.

¿Qué es una SPA?

Single Page Application: la página se carga una vez y React cambia las vistas sin recargar; pide datos al backend por la API.

¿Para qué sirve Docker aquí?

Empaqueta cada componente con sus dependencias para que corra igual en cualquier computador. compose.yaml levanta los 4 contenedores con un comando.

¿Qué es el Kardex?

El registro histórico de todas las entradas y salidas de cada producto. Aquí es inmutable: solo se agregan movimientos.

¿Qué roles hay?

Administrador, Vendedor, Almacenero y Reponedor (más un rol de demostración que los reúne). El rol decide qué módulos y acciones ve el usuario, y el backend lo vuelve a verificar.

Intermedias

¿Por qué Spring Boot y no Node/Django?

Lo exigía el requerimiento RNF-02 y encaja con transacciones de inventario: Spring ofrece transacciones declarativas, seguridad y pruebas integradas, y Java tiene tipado fuerte para un dominio con mucha regla de negocio.

¿Cómo se comunican frontend y backend?

Por HTTP/JSON. Nginx sirve la SPA y reenvía /api al backend. Cada petición lleva un JWT en Authorization: Bearer.

¿Cómo funciona el login?

El backend verifica usuario y hash de contraseña y emite un JWT firmado (HS256) con el rol. El frontend lo guarda en la sesión y lo envía en cada petición; el backend valida firma, expiración y rol.

¿Qué hace Flyway y por qué no ddl-auto=update?

Aplica migraciones SQL versionadas. update cambia el esquema sin dejar registro; con Flyway el esquema es reproducible, revisable en pull requests e inmutable una vez integrado.

¿Cómo evitas vender más de lo que hay?

Transacción + bloqueo pesimista de las filas de inventario + trigger diferible en la base que impide que las reservas superen el stock físico. Tres defensas.

¿Qué es TanStack Query y por qué lo usaste?

Administra el estado del servidor (datos que viven en el backend): caché, estados de carga/error, reintentos e invalidación. Evita copiar datos a un estado global y mantiene las pantallas actualizadas tras cada operación.

¿Cómo validas los formularios?

En el frontend con Zod (mensajes por campo) para la experiencia de usuario, y de nuevo en el backend con Bean Validation y la base con CHECK. Nunca se confía solo en el cliente.

¿Cómo pruebas el sistema?

Backend con JUnit + Testcontainers (PostgreSQL real) y validación contra OpenAPI; frontend con Vitest/Testing Library y axe para accesibilidad; Playwright para E2E; todo corre en GitHub Actions.

Avanzadas

¿Por qué no microservicios?

Las operaciones de inventario, reservas y Kardex deben ser atómicas. En microservicios requerirían transacciones distribuidas (sagas, consistencia eventual) que añaden complejidad sin beneficio a esta escala. Elegí monolito modular y extraje solo el OCR, que sí justifica separarse (lenguaje, carga y ritmo distintos). Está en el ADR-004.

¿Cómo garantizas que los módulos no se acoplen?

Reglas de dependencia (un módulo solo usa el service de otro, solo inventario muta stock) aplicadas en la estructura por paquetes y verificadas en la revisión de cada pull request.

¿Qué pasa si el cliente reintenta una petición por mala conexión?

La cabecera Idempotency-Key hace que el reintento devuelva la respuesta original sin ejecutar de nuevo la operación; se registra en la tabla idempotencia.

¿Cómo evitas que la IA invente SKUs?

La IA solo extrae texto y cantidades. La asignación de SKU la hace un pipeline determinista: normalización de jerga, extracción de medidas y similitud con RapidFuzz contra el catálogo, con penalización fuerte si la medida no coincide. Y un humano revisa antes de usarlo.

¿El agente puede modificar el inventario?

No. Solo invoca funciones de consulta que el backend expone y autoriza por rol (tool calling). No tiene acceso a la base de datos. Hay una prueba que verifica que las herramientas coinciden con el contrato.

¿Cómo manejas la caída de Gemini o de la cuota?

Una lista de modelos con cambio automático al agotarse la cuota, reintento ante saturación, plazos configurables, y el backend marca SERVICIO_NO_DISPONIBLE si el OCR no responde a tiempo. Para el agente, las consultas simples se resuelven por reglas sin Gemini.

¿Por qué bloqueo pesimista y no optimista?

El conflicto de reservar el mismo stock es frecuente y costoso si falla; bloquear la fila y que el segundo espere es más simple y predecible que reintentar. El bloqueo optimista conviene cuando los conflictos son raros.

¿Cómo aseguras la integridad si hay un bug en el código Java?

La base es la última línea de defensa: CHECK de cantidades, claves foráneas con RESTRICT, triggers diferibles para sumas de reservas, Kardex solo-anexión y unicidades. Un estado inválido se rechaza al confirmar.

¿Cómo escalaría el sistema?

Verticalmente primero (el cuello de botella real son las transacciones de inventario). Después réplicas del backend detrás de un balanceador (es sin estado gracias a JWT), réplicas de lectura de PostgreSQL y, si hiciera falta, extraer módulos (por ejemplo reportes) como servicios.

¿Qué es el contrato OpenAPI y qué ganas?

Una especificación de cada endpoint (rutas, datos, errores, roles). Genera una “fuente de verdad” común: las pruebas validan el backend contra ella y el frontend adapta sus tipos, evitando desalineaciones.

¿Qué es RLS en tus migraciones?

Row Level Security de PostgreSQL activada en las tablas como defensa adicional (el backend es el único cliente de la base y Supabase solo se usa como PostgreSQL).

¿Qué mejorarías?

Devoluciones, reportes/tableros, notificaciones, refresco de token, observabilidad (métricas/trazas) y pruebas de carga.
